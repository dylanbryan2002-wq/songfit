## Critical

**C1 — §§5, 8: the existing gate leads to a missing page.** Both 402 branches in `UploadForm` redirect to `/subscribe`, which does not exist. Auto-resume exposes this immediately for returning creators; `create_submission` still enforces the allowance. Alternative: handle both 402 responses with an inline explanation and "Open my latest result," retaining the selected file without automatic retries. Distinguish an in-flight job from an exhausted allowance. Changing the allowance is Dylan's decision, not an incidental landing-page fix.

**C2 — §5: auto-resume needs an explicit, single-use intent.** A fresh blob alone must not start uploading on every signed-in home visit. The global `upload` key can also be overwritten by another tab/account flow. Alternative: use a random pending ID, carry that ID through `next`, and require a matching fresh record before auto-start. Atomically claim it before uploading; guard duplicate effects/clicks. Persist the issued submission ID/path and upload progress state needed for recovery, bound to the authenticated creator. The server's idempotency only helps when retries reuse that ID; current `UploadForm` keeps its target only in component state. On remount, back navigation or uncertain POST success, reconcile the existing submission before requesting another target. If that is too much for Thursday, restore the file but require "Find my songs" explicitly and scope recovery accordingly.

## Important

**I1 — §5; L1: define storage failure and cleanup precisely.** Await IndexedDB transaction completion, not just `put` success, before navigating. Bound blocked/open/write waits; private browsing is not the only failure case. Validate record shape and `0 <= now − savedAt < 30 minutes`; delete expired records when encountered. Remove matching records on replacement, discard, success and sign-out; preserve retryable network failures. Never let cleanup for an old attempt erase a newer selection. OAuth cancellation, `?auth=failed`, missing storage and already-authenticated `?resume=…` need explicit outcomes. Preserve the file on sign-in errors and allow retry. Confirm redirects return to the same origin, including apex versus `www`.

**I2 — §§4–5: privacy copy becomes ambiguous before automatic upload.** "We only read your name and email" reads as a product-wide claim beside a video chooser. Current home copy explicitly discloses storage and third-party analysis; `/privacy` says frames/speech go to Anthropic/OpenAI and videos remain in Supabase. Alternative for Dylan's approval: "From Google, we use your name and email," plus a concise processing disclosure beside Continue and a privacy link. Explain that Continue starts uploading after sign-in. Document the temporary on-device copy and its cleanup; a 30-minute freshness check does not guarantee physical deletion after 30 minutes when the site is closed. "Not shared with other creators" matches the policy more precisely than an unexplained "private."

**I3 — §§5, 8: reuse validation without tightening it accidentally.** `readVideoDuration` returns null on unsupported metadata or timeout; `durationVerdict(null)` deliberately permits server validation. Show unknown duration honestly. Include existing extension checks, reject empty files, and prevent stale asynchronous validation from replacing a newer selection. Cancelling "Change" should retain the current file. Auto-start must call the same upload operation as manual submit, preserve retry behavior, and expose cancel/change before work begins; it currently bypasses the opportunity to enter optional intent.

**I4 — §5.5: a null creator is supported; missing events are a deliberate rules exception.** `events.creator_id` and `logEvent` already allow null. I recommend minimal anonymous `landing_viewed`, `video_chosen` and `sign_in_started` events, documented first, with a short-lived random flow ID, deduplication key, strict payload limits and rate limiting through a narrow server endpoint. Never send filenames or video content; retain service-role-only event writes. Correlate successful OAuth with that flow: existing `signed_up` is a new-account heuristic, not every sign-in. A lone `video_chosen` count cannot measure the requested funnel. If this scope is deferred, explicitly rule an exception to "every creator action," and do not claim landing conversion from post-auth counts. Anonymous uploads would add substantially more cost and ownership/cleanup work than these events.

**I5 — §6: use Google's generated treatment rather than approximate it.** Current Google guidelines allow "Continue with Google" and confirm the proposed light colors, but specify Google Sans Medium, 14/20 text, and web padding of 12 px before the logo, 10 px after it, 12 px after text. Mobile web follows web guidance. Use their HTML configurator/downloaded current logo, retaining Supabase OAuth; 48 px height, 8 px radius and a hand-sized G alone do not establish compliance.

**I6 — §§4, 7–8: the demo is a deliverable, not optional decoration.** A full-width 9:19.5 frame can push the CTA well below the first phone viewport. Cap its height and test a short screen. Keep a real result screenshot when video is missing or autoplay fails; hiding everything restores the original bare-page problem. Show song plus section legibly without sound. `preload` is only a hint and autoplay can override it; use a poster for reduced motion and provide pause. Move the real iPhone OAuth/blob spike before the component build. Test cancellation, storage failure, double-resume, lost POST response and 402, then run typecheck/tests/build.
