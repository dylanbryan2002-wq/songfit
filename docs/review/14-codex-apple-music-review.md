# Apple Music review — Codex, 2026-10-07

(Pasted verbatim by Dylan from the Codex terminal.)

Recommendation: do not enable Apple samples under the proposed permission assumption. Successful catalogue requests establish technical access, not authorization for this experience. The fallback architecture is otherwise reasonable after the fixes below. Reviewed current code and primary sources; no credentials accessed or live playback tested.

## Critical

**C1 — §§2–3, 5.1: MusicKit expressly restricts synchronization too.** Apple's Developer Program License Agreement, §3.3.6(D) says: "MusicKit Content cannot be synchronized with any other content, unless otherwise permitted by Apple in the Documentation". That directly challenges playing a sample against the creator's looping video, even without exporting a combined file. The same section restricts unrelated uses of the APIs, indirect monetization, and playback implementation, including full-song availability. I found no documented exception covering this preview-only, developer-token-only workflow. The separate §3.3.6(F) preview permissions concern Apple Music Feed, not this catalogue API, and also prohibit video synchronization. Alternative: require applicable written permission or a documented exception before enabling this use. Independent audio audition may remove the synchronization issue, but does not resolve the other restrictions automatically. A developer subscription and valid key do not grant those exceptions.

**C2 — §3 types/persistence; A2–A3: Apple picks can lose their candidate link.** Actual `recommend.ts` reconstructs `rowKey` only from `deezer_id`; its `preview_source` writer hardcodes Deezer. `listPickerRows` joins only `candidates(deezer_id)`. Merely adding columns leaves Apple recommendations with null `candidate_id` and no refreshable source. Alternative: carry source/ID through verification, inserts, row identity, recommendation linkage and the picker projection; test a persisted Apple recommendation through render and refresh. The tables do not currently mirror every `VerifiedCandidate` field as §1 implies. Specify which identities are stored versus derived, with legacy Deezer rows remaining readable.

## Important

**I1 — §3 matching/dedupe: reject wrong recordings before ranking.** `DISQUALIFYING_DESCRIPTOR` matches `mix`, not `mixed`; therefore "(Mixed)" can pass loose matching today. Add explicit fixtures for Mixed, remix, demo, live, clean/explicit and remaster variants. A plain-title preference alone cannot prevent a wrong recording when no original is returned. Do not use `contentRating` as evidence of studio provenance; album names are also weak evidence. Prefer an eligible exact plain-title match, then explicitly allowed variants. Filter for available previews before choosing among otherwise equivalent matches, and run `validateSection` against Apple duration converted from milliseconds.

**I2 — §3 dedupe: name keys are a heuristic, not recording identity.** Existing `normalizeKey` retains years/descriptors and differing artist credits, so cross-provider remasters may remain duplicates. Deezer-first is a sensible deterministic preference; retain it. Dedupe with one tested canonical identity policy before minimum-count checks, regeneration and diversification, merging directions. Deferring dedupe until the final picks can leave fewer distinct songs than expected. Equal ISRCs, when available from both sources, provide additional recording evidence; avoid expanding this into an ISRC lookup project this week. Use the same identity policy for two-creator "Couldn't find it" bans so changing providers cannot evade them.

**I3 — §§3, 5.5: 10 requests/second is an experiment, not a safe allowance.** No verified published limit establishes it. Module pacing applies per process; concurrent submissions, regeneration and 15 refreshes per results render multiply demand. Add bounded concurrency, per-call timeout and a total Apple-pass deadline tied to `StageCtx`, leaving time for scoring/explanations. Stop scheduling immediately on 401/403/429; honor a supplied retry delay only within budget. Define 5xx/network behavior. Preserve valid Deezer results and classify unavailable/unattempted Apple lookups separately from confirmed misses/no-sample; otherwise outages provoke unnecessary regeneration. Revisit the existing Deezer outage threshold explicitly rather than accidentally masking it.

**I4 — §§3, 5.4: token cache is fine; reduce credential exposure.** Node crypto with P1363 is appropriate. Use a much shorter token lifetime than the six-month maximum and a compatible refresh margin. Keep key loading/signing in server-only modules, never client-shared configuration or serialized DTOs; log sanitized error categories, not headers, PEMs or tokens. Test signatures with a generated test key and clock-controlled expiry tests. Distinguish absent configuration from malformed credentials. Path-first loading can select a stale path over valid deployment text; define local-path versus production-text precedence explicitly. Do not import/run the probe as application initialization.

**I5 — §§3, 5.2; A4: a URL is not proof of a playable 30-second sample.** Parse empty previews and absent attributes safely; treat malformed responses separately from genuine misses. Measure the four named recordings plus several contrasting genres: actual browser duration, audible opening/hook, offset against the same licensed recording, and iPhone/Android playback. Record IDs/storefront and observations, not audio files. Clamp playback to actual duration and the intended 30-second maximum; do not assume the preview starts at zero in the full song. Fixed `us` is a scope choice, not worldwide availability evidence.

**I6 — §§3–4: close the rules/UI gaps.** `CLAUDE.md` still explicitly requires Deezer verification; record the approved rule change. Update DATA_MODEL, migration and generated types in order; preserve Zod stage contracts. Add Apple to the existing `open_app` destination schema and UI union before use. Update `/privacy`, which currently names only Deezer. Use source-specific attribution and "Listen on Apple Music," consistent with Apple's identity guidance; a shared footer is not evidence that every branding requirement is met. Keep ownership checks and the preview kill switch across both providers.

## Minor
