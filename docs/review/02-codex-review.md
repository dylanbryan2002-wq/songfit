# Codex review — 2026-10-06

## Verdict

**Ship with these changes; do not execute the plan verbatim.** The single-app architecture is appropriate, but the supplied implementations contain deterministic integration failures, a bypassable paywall, payment-processing failures, and an unsubstantiated promise of accurate musical timestamps. Thursday is plausible only if the controller resolves the critical findings first and moves a real deployed upload → recommendation test ahead of admin polish. Keep the automated engine and three results; defer nonessential presentation and catalog work. This is a review of the proposed code and contracts, not a claim that an implementation has passed tests. Task references below refer to `docs/superpowers/plans/2026-10-06-songfit-mvp.md` unless another document is named.

## Critical (blocks Thursday or causes rework)

- [C1] **Model JSON contract — Tasks 2.3, 3.2, 3.6, 3.9** — `extractJson()` returns a string sliced from the first `{` to the last `}`. Candidate generation, scoring, and explanations pass that string directly to an array schema. Even perfect JSON arrays fail; the helper also strips their brackets. Analysis separately calls `JSON.parse`, so changing the helper without changing analysis introduces another failure. **Fix:** establish one parser returning `unknown`, supporting complete JSON objects and arrays after removing optional fences; update every caller and test together. Reject incomplete candidate/score/rank sets, retry malformed output once with the validation error, then fail with the raw response retained for admins. Current silent item dropping, fabricated `0.5` scores, and explanation fallbacks contradict the explicit model-response rules.

- [C2] **Paywall and write authorization — Tasks 0.3/0003, 1.2, 1.3, 4.7** — `canSubmit()` runs only when issuing an upload URL. An authenticated user can repeatedly POST new submission IDs referencing an existing owned video and obtain more runs after their free result. Concurrent submissions before the first result also all qualify. The authenticated Storage INSERT policy bypasses signed-URL issuance and its limits entirely; the submissions INSERT policy permits arbitrary status and video paths so long as `creator_id` is the caller. **Fix:** make submission creation an atomic server/database operation that checks entitlement, reserves at most one unpaid in-flight attempt, validates the issued object path/ID, and is idempotent on submission ID. Consume the free allowance on successful delivery and allow failed-attempt recovery. Remove direct authenticated submission INSERT and unrestricted Storage INSERT if signed uploads are the intended boundary. Rate-limit upload authorizations and run creation, not just already-created submissions. Validate stored size/type and the exact path binding server-side.

- [C3] **Pipeline timeout, resume, and concurrency — Tasks 2.5, 3.10 step 6, 4.7** — Phase 3 replaces the Phase 2 runner instead of wiring its dependency, discarding its injected test interface, persisted-output resume logic, and budget check. The replacement also leaves `stage = "analyze"` after analysis, misclassifying ordinary recommendation failures. Even Phase 2 checks time only before whole stages; a long SDK call or ffmpeg process can cross 300 seconds without persisting failure. The final double-run guard is a read followed by a write, so two requests can both pass. **Fix:** retain one runner, use an atomic database claim with attempt ID/lease expiry, and put that claim inside the shared entry point used by both run routes and admin retries. Pass a deadline through every external call and subprocess; abort/kill them with time reserved for persistence. Save successful expensive substages and commit final recommendations plus `ready` atomically. Retry from stored completion markers, not error-message prefixes; permit stale-lease recovery. Add simultaneous-run, mid-stage timeout, partial-write, and retry tests.

- [C4] **Stripe can permanently lose paid activations — Tasks 0.3, 0.4, 4.4** — `claimStripeEvent()` inserts the deduplication row before activation. If activation fails, the HTTP retry is treated as a duplicate forever. The initial partial unique index on `stripe_subscription_id` also does not support the proposed unqualified `ON CONFLICT (stripe_subscription_id)` upsert; this is a database runtime problem, not something TypeScript will catch. Subscription updates arriving before checkout update zero rows, and delayed checkout can reactivate a canceled subscription. **Fix:** use a normal nullable UNIQUE constraint; atomically commit event completion and entitlement mutation, or maintain recoverable processing/completed states. Reconcile the current Stripe subscription rather than assuming delivery order. Validate the expected subscription product/price, checkout/payment state, nonempty IDs, and creator mapping before granting access. Avoid using mutable creator email as an authorization fallback. Add database-backed tests for failure after event receipt, duplicate delivery, and reversed event order. Stripe explicitly does not guarantee event ordering: [webhook documentation](https://docs.stripe.com/webhooks).

- [C5] **Remaining cross-task contracts prevent compilation or execution — Tasks 0–4** — The pre-flight ledger is incomplete. `logger.ts` exports `log`, while most later code imports `logger`; `createSubmission()` does not accept/persist the `id` supplied by Task 1.3; `getAnalysis()` reads `video_analyses.content_category`, which the migration does not create; Task 2.5 imports/calls `getAnalysisRowRow` although the dependency is `getAnalysisRow`. Task 3.10 redefines database `Row` aliases as insertion payloads and changes replacement return types. `Logo` has a default export but later named imports; `WaitingState` accepts `id` but Task 3.11 supplies `submissionId`. Task 4.2 assumes `FinalRecommendation[]`, different page variable names, and rank-taking card callbacks, whereas Phase 3 supplies a small `RecommendationView[]` and different props. **Fix:** reconcile the actual snippets against one contract before dispatch, preserve generated Row/Insert distinctions, and use a shared creator-facing DTO. Do not send internal candidate scores to the browser merely to satisfy `FinalRecommendation`. Run the complete typecheck/test/build suite after each phase integration, including the earlier pipeline tests.

- [C6] **Exact sections are unverified, and reveal alignment is sometimes false — Tasks 3.2, 3.5, 3.8** — Deezer establishes track identity/duration, not that a chorus occurs at the model's proposed timestamp. Clamping an impossible timestamp to a track's final seconds preserves an explanation about a musical event that may not occur there. Alignment assumes `proposed_start` is a verified hit. For hit H=5 and reveal T=10, clamping `H−T` to zero places the hit at video second 5, not 10. Later fitting can move it again; long-video reveals outside the 12–20-second excerpt cannot align at all. **Fix:** separate proposed segment bounds from an explicit musical anchor, its evidence, and any video placement offset. Align only when the final bounds satisfy `H − start = T` and contain the anchor; otherwise preserve the section without an alignment claim. Reject impossible/too-short tracks instead of inventing a replacement musical moment. Model memory cannot substantiate exact timing: Dylan must choose either a small set of version-specific validated anchors for the automated engine or a clearly communicated estimated-section promise. Do not substitute human approval of every submission. A provider's 30-second preview is not evidence for a full-track timestamp without a known offset.

- [C7] **Deployment and upload prerequisites are late and incomplete — Tasks 0.1, 1.4, 2.1, 4.8** — A 150 MB bucket setting cannot override Supabase Free's 50 MB maximum. Hobby's 300-second Fluid Compute capability does not make it suitable for this commercial subscription app. The deployed Linux ffmpeg/ffprobe binaries, build-script execution, tracing, and function package size are unproven; Task 4.7's replacement config omits the earlier external-package settings. **Fix:** provision the needed paid plans/configuration and deploy a real iPhone MOV/HEVC extraction test immediately, preserving necessary Next configuration. Include a large upload test and verify both binaries actually execute; a skipped local binary test is not a pass. Pin the intended Next/Zod/toolchain versions rather than mixing a Next 15 plan with unrestricted `latest`. Sources: [Supabase upload limits](https://supabase.com/docs/guides/storage/uploads/file-limits), [Vercel function limits](https://vercel.com/docs/functions/limitations), [Vercel Hobby restrictions](https://vercel.com/docs/plans/hobby).

- [C8] **Paid-product music API rights are not established — `docs/RESEARCH.md`, Tasks 3.3, 3.4, 3.9, 3.11** — “We never host audio” does not establish permission to use metadata/artwork/previews in a paid recommendation service. Apple's preview terms require promotional placement, an approved store link/badge and attribution, and prohibit synchronization with video and promotion of other services; the proposed Spotify-only cards do not address those requirements. Deezer's published developer terms contain approval and commercial-use restrictions; I have not established that a newer agreement permits Songfit's use. **Fix:** resolve provider permission before charging, including metadata verification, and disable any preview integration whose use is not permitted. Removing playback alone does not settle Deezer API rights. Keep recommendations distinct from permission to use music in a creator's post, especially branded content. Sources: [Apple Search API terms](https://performance-partners.apple.com/search-api), [Deezer published developer terms](https://cdn-content.dzcdn.net/pdf/CGU-developers.pdf).

## Important (should change before the task is implemented)

- [I1] **Launch sequencing and engine cost — phases 0–4, shared `MODELS`** — Forty tasks with repeated UI/runner replacements leave the most uncertain work until deployment. Fable is configured for analysis, three candidate calls, and scoring; 75 candidates × six reason-bearing dimensions is a large response, with truncation risk at 16,000 scoring tokens. **Fix:** move provider/model smoke calls, hosted migrations, OAuth, and the deployed pipeline ahead of admin polish. Benchmark a faster configured model and concise scoring output on several real clips. Keep 75 candidates unless Dylan changes that decision; propose a smaller shortlist only with his agreement. Log latency, token usage, stop reason, retry count, and cost per stage. At Fable's published $10/M input and $50/M output, an illustrative 20k input + 20k output is **$1.20** before Whisper, explanation, infrastructure, or retries—not a measured submission cost. One hundred such runs would exceed the $99.90 gross from ten first-month subscribers. [Anthropic model pricing and latency](https://platform.claude.com/docs/en/models/fable-5-1/overview).

- [I2] **`waitUntil` works, but is not durable delivery — Tasks 1.3, 2.6, 4.8** — The submission route keeps a self-fetch alive, but checks only rejected fetch promises; HTTP 403/500/504 responses are silently accepted. Preview deployment protection can block the internal call. The caller's timeout still applies to `waitUntil`; setting 300 seconds on the target does not configure the caller. Admin retry invokes the runner directly and bypasses a guard confined to the run route. **Fix:** simplest for Thursday is an authenticated submission route using `after`/`waitUntil(runSubmission(id))` directly with explicit duration, the shared atomic claim, and admin recovery for lost execution. Alternatively retain the self-fetch with a trusted configured origin, explicit response checks, and deployment-protection handling. Neither option guarantees delivery after process termination. Move the same claimed runner to a durable job system only when measured needs justify it. [Vercel `waitUntil` reference](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package).

- [I3] **Matching can verify the wrong recording — Tasks 3.1, 3.3, 3.5** — Prefix matching accepts different titles such as “Stay” and “Stay With Me” by the same artist. Removing every parenthetical/dash suffix treats live, remix, acoustic and sped-up versions as interchangeable, invalidating timestamps. Splitting artists on “and” damages actual band names; ASCII-only normalization loses non-Latin names. **Fix:** require conservative normalized title equality, retain version identity, and reject incompatible versions; normalize featuring credits separately from artist identity. Store the provider's canonical title/artist and recording identifier. Deduplicate verified recordings by Deezer ID before counting success. Try the plain search if strict results contain no acceptable match, not only when strict results are empty. Add adversarial matching fixtures.

- [I4] **Regenerate-once discards useful results and confuses outages with missing songs — Tasks 3.3, 3.10** — The second generation replaces the first verified/unverified sets. Two initial matches plus two new distinct matches still fail, and the first attempt disappears from inspection. Three candidate rows resolving to fewer than three recording IDs also skip regeneration. **Fix:** preserve both attempts, keep verified matches, pass exclusions into regeneration, merge by recording ID, and test for three distinct usable tracks before scoring. Classify network/quota/provider errors separately from genuine no-match responses; retry those with bounded backoff rather than spending another model call on new songs.

- [I5] **Rate limiting and optional previews — Tasks 3.3, 3.4, 3.9** — The Deezer throttle is local to one process, not a shared-IP limit across Vercel instances. All candidate requests enter `Promise.all`; a single hung request holds verification open. iTunes is called for all three picks even when Deezer previews exist, with no shared pacing, and optional preview work delays the result. **Fix:** add bounded concurrency, request deadlines, cache verified lookups, and handle provider errors/429s explicitly. Treat the documented-in-research Deezer quota as an assumption, not an SLA. Call iTunes only for missing previews if permitted, cache/pacing its lookups, and let preview failure yield a usable result without audio. Add preview source/track identity so expired links can be refreshed without re-running recommendations.

- [I6] **The phone sign-in journey contradicts the spec — spec §3, Task 1.4** — The spec promises the chosen video survives OAuth and upload starts automatically. Implementation stores only intent and requires choosing the file again. A `File` cannot be preserved by JSON in `sessionStorage`. The XHR uploader also has no resumable transfer or automatic retry despite the error-handling promise. **Fix:** make the product choice explicit: IndexedDB Blob persistence with quota-failure handling, a tested auth flow preserving the page, or Dylan-approved sign-in-before-file-selection/reselection. For 150 MB mobile uploads, use Supabase's signed resumable upload support; test OAuth return, interrupted cellular upload, MOV/HEVC, rotation, and returning from the background on a real iPhone. [Supabase recommends resumable uploads for files over 6 MB and unstable networks](https://supabase.com/docs/guides/storage/uploads/resumable-uploads).

- [I7] **Sunday metrics are materially wrong — Tasks 3.10, 4.3, 4.5** — `recommendations_ready` omits `creatorId`, so the funnel's distinct-ready-creators count is zero. `by_category` counts ready submissions after joining every event, multiplying each submission by its event count. `Offer.track()` immediately returns for the null submission ID used on `/subscribe`, dropping the actual paywall's views/clicks. **Fix:** record creator attribution on every applicable milestone, count distinct submissions or aggregate before joining, and provide an authenticated creator-level offer-event path. Preserve the first readiness timestamp across retries. Test the SQL against two submissions with repeated events and a payment; present distinct creators reaching recommendations and distinct paid subscribers alongside raw event totals.

- [I8] **Future catalog and durable execution need a little more provenance — shared types, Task 3.10, data model** — Candidate identity/section information is flattened into `generator_reason`; the row mapper drops artwork/URLs and cannot carry `song_id`, a segment ID, retrieval source, or trend observation. Explanation prompt version is exported but never persisted. Delete-then-insert replacements are not transactions. **Fix:** preserve structured section/fit reasons, canonical recording identity, source, optional song/segment references, and separate stage versions with stored outputs. Add attempt/completion markers and atomic stage replacement; this lets a later worker use the same runner. Empty catalog tables are harmless, but embeddings and trend retrieval do not need implementation this week. Do not permanently choose one segment per song in the data contract merely because launch diversification returns distinct songs.

- [I9] **“More current” and dialogue fit overclaim their evidence — Tasks 2.2, 3.2, 3.6, 3.7** — The current-direction prompt has no trend feed or dated evidence; generation order gives cross-direction duplicates to `safe`. Rank one can carry “Unexpected,” while “Best fit” can appear on a lower rank. Whisper output length alone does not distinguish spoken dialogue from singing; the rule calls any section without words matching its regex “mostly instrumental,” including unknown sections. **Fix:** retain direction memberships during deduplication, distinguish overall rank from generation direction, and have Dylan approve labels that reflect what is known. Treat trend status and vocal presence as unknown unless supported; request explicit spoken-dialogue and section-vocal assessments instead of inferring absence from prose. Do not claim current popularity or platform availability merely because Deezer matched a song.

- [I10] **Failure and billing UX promise work that is not happening — spec §5, Tasks 1.5, 4.1–4.4** — A terminal failure polls forever saying “we'll keep trying,” although only an admin can retry. The thanks page says “You're in” before entitlement exists. “Cancel anytime” has no cancellation path. Feedback can mark multiple picks selected or selected-and-rejected, and client state resets on refresh. **Fix:** show an honest failed/recovering state and a bounded recovery path; poll entitlement after checkout; configure a Stripe-hosted cancellation/portal path. Make selection mutually exclusive and persist/load feedback state. Log actions only after a real owned recommendation was updated, and deduplicate retryable events.

## Answers to questions 1–7

1. **Will it ship?** Not reliably as written. Resolve C1–C8, deploy the risky media/model path immediately, and finish payment plus accurate metrics before polish. OAuth file preservation and timestamp truthfulness need explicit product rulings; provider rights and paid-plan setup are external dependencies. A Wednesday deployed phone test should be the release gate, not Task 4.8's final discovery step.

2. **Architecture/data model?** Keep one Next app, typed stage boundaries, Supabase, and the automated engine. Add atomic claims, completion markers, transactional writes, and structured provenance now. Those changes permit a worker/catalog later without rewriting the product. Defer retrieval infrastructure and detailed admin presentation.

3. **Engine correctness?** Fix the shared parser first. Then verify recording versions conservatively, merge regeneration attempts, count distinct usable IDs, and reject unsupported sections. Model-generated timestamps and popularity are hypotheses; clamp arithmetic and a second model's agreement do not verify them. Reveal alignment requires a valid anchor and feasible final bounds.

4. **Runtime?** Technically viable for an MVP if benchmarked. With Fluid Compute, documented maximums are 300 seconds on Hobby and 800 on Pro; this commercial app should use Pro. `waitUntil` has the caller's timeout and no durable-delivery guarantee. A direct background runner in the submission function is the cheapest simplification; retain manual stale-run recovery and measured deadlines. Use a durable worker if real runs cannot fit safely. [Vercel limits](https://vercel.com/docs/functions/limitations), [Hobby policy](https://vercel.com/docs/plans/hobby), [background lifetime](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package).

5. **Auth/security/money?** The basic Google SSR, private bucket, ownership checks, and internal token are sensible. The launch blockers are bypassable submission authorization, non-atomic free-run admission, race-prone execution, and prematurely acknowledged Stripe events. Enforce entitlement at the operation that spends money and make webhook processing recoverable.

6. **Cross-task consistency?** There are substantial unresolved mismatches despite the ledger: JSON contract, logger export, submission ID, analysis category, doubled query name, Row/Insert types, runner replacement, waiting/card/page props, and default/named exports. Migration numbers themselves look reconciled. Correct the plan snippets and run full integration checks rather than relying on per-task mocked tests.

7. **Anything else?** Provider preview/API rights are a launch dependency; a recommendation is not a music-use license. Rate limits apply across submissions, optional previews should not block results, and 150 MB phone uploads need resumability and the right Storage plan. Measure actual token cost and repeated-use economics before treating $9.99/month as sustainable. Record distinct creators and paid subscriptions accurately so Sunday's deck measures the promised funnel.
