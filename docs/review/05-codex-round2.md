**Cross-task mismatches still present after the rewrite**

1. **Tasks 2.5 → 3.10: runner contract breaks at compilation and runtime.** `RunDeps.recommend(id, ctx: StageCtx)` is assigned `recommendSubmission(id, deps: RecommendDeps = defaultDeps)`. The real invocation treats `{ deadlineAt }` as `deps`, then calls nonexistent `deps.getSubmission`. Give the orchestrator a context parameter and pass it through generation, verification, scoring and explanations; keep dependency injection separate.
2. **Tasks 0.4 → 2.4/3.10: database contracts still disagree.** Task 2.4 imports `updateSubmission`, but 0.4 exports `setSubmissionAnalyzed` and supplies no `updateSubmission` implementation. Task 3.10 declares `replaceRecommendations: (...) => Promise<void>` while 0.4 returns `Promise<RecommendationRow[]>`; the default dependency assignment is incompatible.
3. **Tasks 1.5 → 3.11: waiting props regress.** `WaitingState` requires `initialStatus`; 3.11 passes `status` instead. Its prose suggests adding an optional prop but does not remove/satisfy the required one or connect it to failure state. Retain the original prop contract.
4. **Tasks 3.11 → 4.2: results wiring targets nonexistent code.** The page has `sub`, `recs`, and a `ResultsView`, not `submission`, `recommendations`, or an inline card map. The replacement uses those nonexistent variables. Card callbacks accept `number`, while `ResultsClient` supplies handlers restricted to `1 | 2 | 3`; strict function typing rejects this. Replacing `ResultsView` also drops its heading and required section-estimate footer.
5. **Tasks 0.2/header → 3.7: duplicate shared definitions disagree.** The header defines `DIRECTION_LABEL.safe = "Safe bet"` and `BEST_FIT_LABEL`; 0.2’s “exact copy” and tests instead use `safe = "Best fit"` and omit `BEST_FIT_LABEL`. Task 3.7 works around this with another label map. Pick one definition and update its tests.
6. **Tasks 0.2 → 2.5/3.8/3.9: proposed tests contradict their dependencies.** `PipelineError` prefixes messages with `[analyze]`, but runner tests expect unprefixed messages. Section tests compare `34.2 - 14.2` exactly to `20` (Node returns `20.000000000000004`). Explanation tests change `title` to “Song 1/2” but leave canonical titles as “Blinding Lights”; the implementation correctly uses canonical titles for Spotify/iTunes, so those expectations fail.
7. **Tasks 0.1 → 4.5: strict indexing remains unreconciled.** `noUncheckedIndexedAccess` is enabled, but `median()` returns/operates on possibly undefined indexed elements. Also, `describe.skipIf(...)` still evaluates the suite callback: its unconditional `createClient(url ?? "", key ?? "")` defeats the claimed no-env skip. Add the SQL fixture helper before migration application and assert exact fixture deltas so multiplication is caught.
8. **Tasks 0.1/4.3/4.4 → `.env.example`: names/counts disagree.** Task 0.1 demands exactly 14 keys; the existing template has 15 including `STRIPE_CUSTOMER_PORTAL_URL`. Tasks 4.3/4.4 actually consume `NEXT_PUBLIC_STRIPE_PAYMENT_LINK_URL` and `NEXT_PUBLIC_STRIPE_CUSTOMER_PORTAL_URL`, absent from the current template, although 4.3 later instructs adding them. Reconcile the template and acceptance check, preserving the chosen portal.
9. **Tasks 0.3/3.10 → `docs/DATA_MODEL.md`: schema/provenance drift.** The migration includes candidate `artwork_url`, `deezer_url`, `preview_url`, and `aligned_to_moment`, which the current model document omits; the candidate mapper also omits those values. Task 3.10 overwrites `versionOf` by normalized key on regeneration, so an original retained recording can be falsely stamped `#2`.

**Blockers on Task 0.1 → 1.7**

1. **Task 0.2 has a deterministic failing test.** For `extractJson("{not json")`, the missing closer takes the “no JSON value found” branch, while the test asserts `/invalid JSON/`. Align the error contract/test before the Phase 0 gate.
2. **Tasks 0.4 → 0.5 fail typechecking on event metadata.** `logEvent` accepts `Record<string, unknown>` and passes it to the generated `EventInsert.metadata: Json`; arbitrary `unknown` values are not JSON. Validate/narrow metadata or type the boundary as `Json`.
3. **Task 0.5’s mock cannot initialize as written.** Its hoisted `vi.mock` factory reads a top-level `const insertEvent` before initialization when the static import loads `events.ts`. Use `vi.hoisted` or construct the mock inside the factory. Task 4.1 repeats the same pattern later.
4. **Task 0.3’s schema-check script is outside package resolution.** `/tmp/check-schema.mjs` imports `@supabase/supabase-js`, but installation is under the repository; Node resolves bare ESM imports relative to the script, not the shell’s working directory. Put/run the check under the project or supply an explicit resolvable module path.
5. **Tasks 0.1 → 1.4 fail strict typechecking in the uploader.** `if (prev.length) upload.resumeFromPreviousUpload(prev[0])` still passes a possibly undefined element under `noUncheckedIndexedAccess`. Bind and check the element, and match its upload identity to the currently authorized path before resuming.
6. **Tasks 0.3/1.7 must include the already-approved infrastructure setup.** Move the Vercel Pro/Supabase Pro and global 150 MB Storage configuration from 4.7 ahead of the deployed large-file test. The bucket-level limit alone is not the complete configuration. The 65-second health request only proves survival past 60 seconds, not the stated full 300-second budget.
7. **The early env gate is impossible as specified.** Resolve the 14-versus-15-key contradiction above without deleting the portal setting. Task 0.7’s provider checks also require supplied keys and an installed ffmpeg binary; it only smoke-tests the text model, so its success does not establish analysis-model access.

The existing phase gates should remain. Repair their snippets and test contracts before dispatch; later runner, Stripe and results defects must also be fixed before declaring the full launch path executable.
