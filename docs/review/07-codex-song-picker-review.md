# Song picker review — Codex, 2026-10-07

(Pasted verbatim by Dylan from the Codex terminal.)

Recommendation: keep the video-and-sounds layout, but resolve C1 before enabling previews and cut automatic alignment from launch. P1–P4 together exceed a safe one-day estimate given the Thursday deadline. Review based on current repository code and primary sources; no implementation changes or device tests performed.

## Critical

**C1 — §§4, 6; P1: preview permission is not established.** Deezer's published [developer terms](https://cdn-content.dzcdn.net/pdf/CGU-developers.pdf), §2, require application approval before online use; §IV prohibits commercial gain. The document's age/applicability needs clarification, but a reachable public endpoint and CORS do not establish permission for this paid product or audiovisual synchronization. Alternative: obtain applicable written permission covering this use; meanwhile ship the layout, recommendations and outbound links with previews disabled. This also warrants checking the existing commercial API dependency, not merely waveform processing. iTunes is not a synchronized-preview fallback: its [Search API terms](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/) explicitly restrict synchronization with other media.

**C2 — §§5–6: the interface still conflates two timelines.** A scissors control and tick followed by "Use 0:43–0:58" imply the auditioned edit was saved as that section. The estimates footer does not explain the mismatch. Alternative: label playback "30-second sample · different from suggested section"; label trimming "Adjust sample playback"; state beside the full-track instruction that trimming does not change it. Keep draft audition, saved song choice and full-track timestamps separate. Never infer a full-track offset from preview-relative seconds.

## Important

**I1 — §6; P2: one gesture is necessary, not a synchronization guarantee.** [WebKit's policy](https://webkit.org/blog/6784/new-video-policies-for-ios/) distinguishes direct click-handler playback from later readiness callbacks. Fetching the URL or decoding before `play()` loses that direct chain; React state/effect playback has the same risk. Prefetch URLs, set the persistent element's source imperatively, and invoke both plays without awaiting between them. Handle each promise, loading, failed seeks and stale song-switch completions. Test cold cellular playback, rapid switches, interruption/resume and Low Power Mode on the actual phone. A second explicit Play button is a reasonable fallback; "warming" alone is not proof.

**I2 — §6; P2/P4: define the loop contract before implementation.** Use actual loaded preview duration, not Deezer track `duration` (full-song length). Define `L = min(videoDuration, previewDuration)` and video time as `audio.currentTime − windowStart`; videos longer than L audition only their first L seconds. For ≥30-second videos a 30-second preview leaves no draggable range. Show that limitation and disable trimming. `requestAnimationFrame` is a foreground drift check, not a dependable background loop boundary. Pause both on page hide, coordinate stalls/seeks, and suppress repeated corrections while seeking. Retain an explicit pause control. If the spike fails, use independent audio audition and remove sync claims.

**I3 — §6; P4: the loudest peak is not a musical anchor.** `aligned_to_moment` describes the estimated full-track section, not this preview. Amplitude can identify a loud transient, not the hook or intended hit. Alternative: omit automatic `P − T` and the alignment claim. If useful later, mark the video moment alone and let users align by ear. This cuts analysis, waveform dependencies and misleading certainty.

**I4 — §§6–7: waveform decoding is technically defensible, contractually unconfirmed.** In-memory decoding without persistence differs from offline storage, but the [Deezer guidelines](https://developers.deezer.com/guidelines) do not explicitly authorize this processing. Do not claim compliance from that distinction alone. Pending C1, cut the waveform; use an honest flat time ruler/range input if authorized playback proceeds. Fake waveform peaks falsely imply analysis; server-side peaks introduce more processing and do not solve permission. Follow actual logo/attribution requirements rather than assuming a text footer suffices.

**I5 — §6; P1: the proposed DTO cannot supply the design.** `deezer_id` lives on candidates as text; `RecommendationView` omits `aligned_to_moment`, and playback also needs video duration. Add an explicit query-layer projection that returns only approved fields, validates identifiers and preserves nulls; do not expose candidate scores. Prefer the existing string ID convention. Keep engine persistence schemas unchanged. Parse the preview response with Zod, distinguish unavailable preview from provider failure, and make `{duration}` explicitly preview duration or omit it until media metadata loads. Renumber Phase 4's planned `0004_metrics.sql` after this migration.

**I6 — §6; P3: extend the existing atomic feedback operation.** `markRecommendationFeedback` already calls `set_recommendation_feedback`; do not separately save trim and selection. A new migration should extend the RPC to validate the target before clearing selections and save the offset atomically. Require owner, ready status, valid rank and finite bounded offset; reject clears selection, select clears rejection. Serialize by submission for concurrent requests and test concurrent selects/invalid targets. Preserve rollback/error UI, server-derived refresh state and retry-safe event semantics. Keep feedback orchestration in `src/feedback`, database access in queries, and the route thin.

**I7 — §§6–7: metrics and billing hooks are incomplete.** Only confirming should emit `recommendation_selected`; audition must not inflate the pick funnel. Register and implement copy, outbound destination, explanation-toggle and trim interactions before use; log preview on actual playback and trim on commit, not every frame. Preserve first-owner-only `recommendations_viewed`, `all_rejected`, offer hooks after choice/all-rejected and retry behavior. Existing `create_submission` gates subsequent submissions; do not gate listening again or hide the free ready result. Define trim cancel versus trim confirm versus song confirm.

**I8 — §7: put feasibility before persistence and reserve billing time.** Run the smallest authorized P2 spike before adding trim storage. P3 contains feedback, state recovery and screen integration: it is not merely medium UI work. Cut P4 first, then automatic looping/drift correction if necessary; retain video, rows, explanation, selection/rejection and copy/open actions. Ship paywall/webhook and funnel checks before waveform polish. Add ownership, save-failure and concurrent-feedback checks to P5; a playback-only phone test misses those launch risks.

## Minor

**M1 — §6: constrain and recover preview requests.** Authentication does not enforce three calls per view. Prefer submission/rank lookup with ownership and a small rate limit; existing pacing is process-local. Permit one bounded refresh for expired URLs rather than a rigid three-call lifetime cap. Missing audio must leave selection and explanation usable.

**M2 — §6; P4/P5: make compact controls usable.** Separate row playback from scissors/check/reject buttons, provide accessible names and generous touch targets, and support keyboard/range-input trimming. Test sheet scrolling with browser chrome and safe-area insets. Open-app actions need web fallbacks and must not imply a song was inserted.
